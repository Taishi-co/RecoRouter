# 三端产品与三服务拆分 PRD

日期：2026-06-04
更新：2026-06-05
状态：已按新版设计稿补充，待启动改造
设计稿：`design.pen`
目标：基于更新后的设计稿，将现有 RecoRouter 拆成 B 端无人车小程序、C 端商城小程序、Web 管理运营端，并按业务边界拆出 `vehicle-api`、`mall-api`、`platform-api` 三个后端服务。

## 1. 背景

当前代码是单体形态：

- 一个 Taro 应用同时承载企业、车主、需求方、商城、运营端页面。
- 一个 Rust API 同时承载无人车业务、商城业务、支付、钱包、转账、COS 等能力。
- 商城能力已有雏形，但与 B 端账号、地址、订单支付、后台入口混在一起。

新的产品方向是明确拆分：

- B 端无人车就是无人车业务。
- C 端商城就是社区团购/本地生活商城业务。
- 公共能力只负责支付、退款、转账/分账执行、COS、审计等基础能力，不承载业务规则。

## 3. 产品目标

第一期目标：

- 上线一个独立 C 端商城小程序，品牌为 `叁友甄选`。
- 保持 B 端无人车小程序稳定，移除商城耦合。
- Web 管理端按三模块组织：无人车运营、商城运营、平台能力。
- 后端形成三个服务边界：`vehicle-api`、`mall-api`、`platform-api`。
- Redis、PostgreSQL、COS 允许共用实例，但必须做逻辑隔离。
- 支付、退款、转账、COS、审计由公共服务统一执行；业务规则仍在业务服务内。

非目标：

- 第一阶段不做完整微信分账系统。
- 第一阶段不做完整财务对账中心。
- 第一阶段不打通 B/C 用户体系。
- 第一阶段不让商城订单自动调用真实无人车调度。
- 第一阶段不重做一个复杂客服 IM，只做客服会话/工单/知识库闭环。

## 4. 用户与角色

| 角色 | 入口 | 主要目标 |
| --- | --- | --- |
| B 端企业用户 | 无人车小程序 | 发布/调度配送需求、管理车队和站点 |
| B 端车主/运力方 | 无人车小程序 | 管理车辆、接单、完成运输、收款、提现 |
| B 端需求方 | 无人车小程序 | 发布运输需求、确认费用、支付运费 |
| C 端消费者 | 商城小程序 | 浏览商品、下单、支付、查订单、售后 |
| 商城运营 | Web 管理端 | 管商品、订单、退款、活动、客服 |
| 无人车运营 | Web 管理端 | 管用户、车辆、订单、佣金、异常 |
| 平台财务/管理员 | Web 管理端 | 管支付、退款、转账、审计、COS 配置 |

## 5. 总体架构

```text
B端无人车小程序  ->  vehicle-api  -> vehicle DB/schema
C端商城小程序    ->  mall-api     -> mall DB/schema
Web管理运营端    ->  vehicle-api / mall-api / platform-api

vehicle-api  -> platform-api -> 微信支付/转账/COS
mall-api     -> platform-api -> 微信支付/退款/COS

微信支付通知/退款通知/转账通知 -> platform-api -> 业务服务事件/回调
```

服务职责：

| 服务 | 职责 | 不负责 |
| --- | --- | --- |
| `vehicle-api` | 无人车用户、车辆、需求、运单、佣金业务状态、钱包业务账本 | 商城商品、商城订单、微信底层支付执行 |
| `mall-api` | 商城用户、商品、购物车、商城订单、售后、客服、活动、商城后台 | 无人车调度、车辆资产、B 端佣金规则 |
| `platform-api` | 支付单、退款单、转账单、分账执行、微信通知、COS 凭证、审计、幂等、对账基础 | 商品规则、车辆规则、业务订单状态机 |
| `shared` | 错误响应、配置、日志封装、微信签名 SDK、COS SDK 封装 | 运行时业务流程 |

## 6. 基础设施策略

Redis、PostgreSQL、COS 可以共用基础设施，但必须隔离命名空间。

| 基础设施 | 策略 |
| --- | --- |
| PostgreSQL | 优先三个 database：`vehicle`、`mall`、`platform`；退一步使用三个 schema |
| Redis | 统一实例，key 前缀隔离：`vehicle:*`、`mall:*`、`platform:*` |
| COS | 统一 bucket，key 前缀隔离：`vehicle/*`、`mall/*`、`platform/*` |
| 日志 | stdout/tracing 统一采集；服务名、request id、business id 必须入日志 |

权限规则：

- `vehicle-api` 不能访问商城库表。
- `mall-api` 不能访问无人车库表。
- `platform-api` 不能直接修改无人车订单或商城订单。
- 支付、退款、转账最终事实落在 `platform` 数据库。
- 业务订单最终状态落在各自业务数据库。

## 7. B 端无人车小程序

设计依据：`KTEak`

### 7.1 页面范围

第一期按 `KTEak` 的 6 个手机页整理，不再保留商城入口：

| 设计页 | 产品含义 | 必须实现 |
| --- | --- | --- |
| `首页登录 · 角色选择` | B 端无人车取送货入口，说明需求方、运力方、企业调度三类场景 | 角色/场景入口、核心指标、待办、快捷入口 |
| `需求方 · 发单与追踪` | 需求方发单、费用确认、运输节点追踪 | 发单表单、线路/货品/时段、费用、订单进度 |
| `运力方 · 接单与车辆状态` | 运力方接单和车辆实时状态 | 可接订单、车辆电量/里程/温度、上线/暂停/报修 |
| `企业调度 · 运力看板` | 企业视角调度与区域看板 | 今日单量、准点率、异常数、区域任务分布、调度建议 |
| `消息客服 · 运单协同` | 运单消息、客服和异常协同 | 通知列表、运单对话、快捷回复、异常上报 |
| `个人中心 · 账号与企业` | 账号、企业认证、钱包、车辆与服务设置 | 账号信息、认证状态、钱包指标、企业资料、车辆入口 |

保留但不作为本轮视觉主入口的能力：

- 钱包明细、提现记录、微信收款绑定从个人中心进入。
- 车辆照片、准入资料、出租/自营状态从车辆详情进入。
- 历史通知、佣金通知、提现通知从消息页进入。

### 7.2 核心业务流程

需求发布与接单：

1. 需求方发布运输需求。
2. 车主/运力方接单。
3. 双方确认费用。
4. 运输开始。
5. 运输完成。

运费与佣金：

1. 运输完成后，需求方支付运费。
2. `vehicle-api` 计算平台佣金金额。
3. 如果佣金金额 `<= 0`，订单直接完成，运费入账运力钱包。
4. 如果佣金金额 `> 0`，车主进入佣金支付流程。
5. 车主支付佣金后，后台确认或自动确认。
6. 订单完成，车辆恢复可接单状态，运费入账钱包。

钱包与提现：

1. 完成订单产生 `fare_credit` 钱包账本。
2. 车主绑定微信收款账号。
3. 发起提现。
4. `vehicle-api` 冻结业务钱包余额。
5. `platform-api` 调用微信商家转账。
6. 转账成功、失败、待用户确认等状态回传给 `vehicle-api`。

企业调度与运力看板：

1. 企业用户进入运力看板。
2. 查看今日单量、准点率、异常数和区域任务分布。
3. 对异常运单进入消息客服或异常工单。
4. 调度动作只影响无人车业务数据，不调用商城订单。

车辆状态与异常协同：

1. 运力方查看车辆电量、里程、温控状态。
2. 车辆可执行上线、暂停、报修等业务动作。
3. 报修或异常上报形成无人车异常工单。
4. 异常工单同步到 Web 管理端锐途运力模块。

### 7.3 后端要求

- 保留 B 端 `users`、`user_roles`、`orders`、`vehicles`、`demands` 等业务表。
- 将当前单体支付直接改订单的逻辑改为接收 `platform-api` 事件。
- 佣金计算规则留在 `vehicle-api`。
- 零佣金是正式业务路径，不是异常路径。
- 钱包业务账本留在 `vehicle-api`；微信转账执行迁移到 `platform-api`。

### 7.4 验收标准

- B 端小程序没有商城入口。
- 原有运输订单主链路可跑通。
- 三类入口需求方、运力方、企业调度都能进入对应页面。
- 企业调度看板不会展示商城订单或商城商品。
- 车辆状态页能展示车辆健康指标并产生异常工单。
- 消息客服页能关联运单和异常。
- 运费支付成功事件能正确推进订单状态。
- 零佣金订单自动完成并入账钱包。
- 有佣金订单能进入佣金支付/确认流程。
- 提现状态能从平台服务同步回业务钱包。

设计里的关键业务点必须进入需求范围：

- 首次或切换场景时必须选择社区自提点，购物车、确认订单和订单详情都要展示当前自提点。
- 支付成功后展示提货码，例如设计中的 `A739`，并展示群/团信息。
- 团长中心不是普通个人中心的装饰，需要有待核销、待发货/待处理、分享团购等后台数据来源。
- 邻里圈第一期可以是运营配置内容流，但必须有数据模型和开关，不能硬编码在前端。
- 消息设置影响商城通知订阅和站内消息展示，不能复用 B 端通知配置。

### 8.2 核心业务流程

购买链路：

1. 用户进入商城小程序。
2. 微信登录或静默创建商城用户。
3. 浏览商品并加入购物车。
4. 选择地址并提交订单。
5. 选择或确认社区自提点。
6. `mall-api` 原子锁定/扣减库存。
7. `mall-api` 向 `platform-api` 创建支付请求。
8. 用户拉起微信支付。
9. `platform-api` 接收微信支付通知。
10. `platform-api` 通知 `mall-api` 支付成功。
11. `mall-api` 将订单推进到待备货/待自提，并生成提货码。

团长/自提履约：

1. 支付成功订单进入对应自提点的履约队列。
2. 团长在团长中心查看待核销订单。
3. 用户到店出示提货码。
4. 团长核销后 `mall-api` 记录核销人、核销时间和核销渠道。
5. 核销成功后订单进入已完成或待评价状态。

售后退款：

1. 用户提交售后申请。
2. 商城运营审核。
3. `mall-api` 向 `platform-api` 发起退款请求。
4. `platform-api` 调用微信退款。
5. `platform-api` 接收退款通知并通知 `mall-api`。
6. `mall-api` 更新售后和订单状态，必要时回滚库存。

客服工单：

1. 用户从订单或客服中心创建会话。
2. 客服可在 Web 管理端查看会话和工单。
3. 工单可关联订单、售后、退款。

- `mall_admin_users` 或独立运营账号/权限表

关键规则：

- 商城不复用 B 端 `users.role`。
- 商城不复用 B 端 `address_books`。
- 商城支付不直接写 `payments` 表，应调用 `platform-api`。
- 商城退款必须调用 `platform-api`，不能只改业务状态。
- 库存扣减必须是原子操作，不能先查后扣导致超卖。
- 未支付订单必须超时关闭并释放库存。
- 提货码必须唯一、可核销、可追踪核销人。
- 自提点、团长、配送时段属于商城业务数据，不进入 `platform-api`。
- 邻里圈内容、首页配置、消息设置必须由后端返回，不硬编码在小程序。

### 8.4 验收标准

- 商城小程序使用独立 appid、独立页面列表、独立构建上传。
- 首页、详情、购物车、确认订单、支付、订单、售后、客服、我的可用。
- 16 个设计页对应的一级页面或等价入口均可访问。
- 自提点选择、提货码展示、团长核销主链路可用。
- 商城用户、地址、订单数据不写入 B 端表。
- 微信支付成功后订单状态自动更新。
- 未支付订单超时关闭并释放库存。
- 售后审核后能触发真实退款请求或平台退款任务。

## 10. 支付、退款、转账与分账

### 10.1 基本原则

业务服务负责算账，平台服务负责执行。

```text
vehicle-api 计算无人车订单分账/佣金规则
mall-api    计算商城订单分账/供应商结算规则
platform-api 执行支付、退款、转账、分账计划、幂等、对账、审计
```

`platform-api` 不直接查商品表、车辆表、业务订单表。

### 10.2 支付

支付请求由业务服务创建：

- `business_type`: `vehicle_fare`、`vehicle_commission`、`mall_order`
- `business_id`: 业务订单 ID
- `amount_cents`: 支付金额
- `appid`: 对应小程序 appid
- `payer_openid` 或登录 code
- `callback_url` 或事件 topic
- `idempotency_key`

平台服务负责：

- 创建支付流水。
- 调用微信 JSAPI 预支付。
- 返回小程序支付参数。
- 接收微信支付通知。
- 幂等处理重复通知。
- 通过回调/事件通知业务服务。

### 10.3 退款

商城退款：

- 退款申请、审核、业务原因在 `mall-api`。
- 微信退款调用、退款流水、退款通知在 `platform-api`。
- 退款成功后 `mall-api` 更新售后和订单状态。

无人车退款：

- 第一阶段不作为主流程。
- 如果后续存在运费退款，规则在 `vehicle-api`，执行在 `platform-api`。

### 10.4 商家转账/提现

无人车提现：

- 钱包账本、可提现余额、冻结余额在 `vehicle-api`。
- 微信商家转账创建、查单、通知、重试在 `platform-api`。
- `NOT_ENOUGH` 等可重试错误必须保留原商户单号重试。

商城供应商结算：

- 第一阶段不做自动供应商结算。
- 后续供应商应收金额由 `mall-api` 计算，`platform-api` 执行转账或分账。

### 10.5 分账

第一阶段要求：

- 建立平台分账计划模型和管理端查看能力。
- 业务服务可以提交分账计划草案。
- 平台服务做金额校验、幂等、审计。
- 不要求第一阶段完成真实微信分账 API。

后续真实分账：

- 无人车分账逻辑留在 `vehicle-api`。
- 商城分账逻辑留在 `mall-api`。
- `platform-api` 接受标准分账计划并调用微信分账。

示例分账计划：

```json
{
  "businessType": "mall_order",
  "businessId": "mall_order_123",
  "paymentId": "pay_123",
  "totalAmountCents": 10000,
  "items": [
    {
      "receiverId": "supplier_a",
      "amountCents": 7000,
      "reason": "商品货款"
    },
    {
      "receiverId": "platform",
      "amountCents": 2000,
      "reason": "平台服务费"
    },
    {
      "receiverId": "delivery",
      "amountCents": 1000,
      "reason": "配送费"
    }
  ]
}
```

平台校验：

- 明细金额总和不能超过可分账金额。
- 接收方必须在平台登记且状态有效。
- 同一业务单不能重复执行同一分账阶段。
- 已退款或部分退款后要锁定或调整分账计划。

## 11. 服务间接口要求

### 11.1 服务间鉴权

所有内部调用必须带服务身份：

- `X-Service-Name`
- `X-Request-Id`
- `X-Timestamp`
- `X-Signature`

签名可第一阶段使用共享 secret + HMAC，后续升级 mTLS 或网关签名。

### 11.2 事件回调

平台到业务服务的事件：

- `payment.succeeded`
- `payment.failed`
- `refund.succeeded`
- `refund.failed`
- `transfer.succeeded`
- `transfer.failed`
- `transfer.waiting_user_confirm`
- `split_plan.updated`

事件要求：

- 至少一次投递。
- 业务服务必须幂等。
- 事件体包含 `event_id`、`business_type`、`business_id`、`platform_record_id`、`occurred_at`。
- 失败投递进入重试队列，管理端可查看。

## 16. 验收总表

| 领域 | 验收 |
| --- | --- |
| 服务拆分 | 三个后端可独立启动、独立健康检查、独立 DB/schema |
| 数据隔离 | Mall 不写 Vehicle 表；Vehicle 不写 Mall 表；Platform 不写业务订单表 |
| 支付 | 商城订单、无人车运费、无人车佣金都通过 `platform-api` 支付 |
| 退款 | 商城退款进入 `platform-api` 退款流水 |
| 转账 | 无人车提现通过 `platform-api` 商家转账 |
| 分账 | 第一阶段有分账计划模型和管理端，不要求真实微信分账执行 |
| 小程序 | 无人车和商城使用不同 appid、不同页面列表、不同构建上传 |
| Web 管理端 | 锐途运力、叁友甄选、超级管理员三模块清晰，菜单和权限不混淆 |
| 设计稿一致性 | B 端 6 页对齐 `KTEak`，商城 16 页对齐 `XuEiy`/`CctBE`，Web 58 页对齐 `mUU7R` |
| 履约 | 商城支付成功后生成提货码，团长可核销，自提点状态可追踪 |
| 权限 | 超级管理员可配置账号、角色、菜单权限、数据域权限 |
| 可观测性 | request id、service name、business id、platform record id 可追踪 |

## 17. 风险与约束

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 三服务一次性拆分过大 | 15 天交付压力高 | 先同 repo 拆服务，暂不多 repo |
| 支付通知重复/乱序 | 订单状态错误 | 平台和业务服务都做幂等 |
| 商城库存并发 | 超卖 | 原子扣减、超时关单释放 |
| 退款只改业务状态 | 资金不一致 | 退款必须走 `platform-api` |
| 公共服务承载业务规则 | 重新耦合 | 业务算账，平台执行 |
| 共用 PG/Redis/COS 导致串数据 | 安全和稳定风险 | schema/key/prefix/权限隔离 |
| 旧 migration 被修改 | 部署风险 | 只新增 migration，不改历史 |
| 设计稿和实现范围不一致 | 子 agent 开发偏航 | 设计稿 frame 作为功能合同，差异必须写入说明 |

## 18. 开发前置检查

开始分发子 agent 前，必须确认：

- 商城小程序 appid 已确定。
- 同一商户号已能绑定商城 appid。
- 支付回调域名、退款回调域名、转账回调域名已规划。
- PostgreSQL DB/schema 命名已定。
- Redis key prefix 已定。
- COS bucket 和 key prefix 已定。
- Web 管理端是否继续使用当前 Taro H5 形态已定。
- 第一阶段是否需要真实微信分账 API，默认不需要。
- 生产服务器、微信商户、COS 等敏感凭据只进入部署环境变量或密钥管理，不写入仓库文档、PR 描述和提交记录。
- 每个 agent 开始前先输出接口/表/页面清单，确认不跨服务写库。

启动改造顺序：

1. Agent A、B、C 先并行输出各自数据库和接口清单。
2. Agent D、E 先完成独立小程序路由、页面壳和 API client 边界。
3. Agent F 先完成 Web 三模块路由、菜单权限和 58 页页面壳。
4. Agent G 在三服务健康检查和回调配置稳定后介入联调部署。
5. 支付/退款/转账链路必须先在测试环境闭环，再接生产配置。
